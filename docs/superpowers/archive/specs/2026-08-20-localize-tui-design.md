# Localize the TUI (ratatui client) design

> **Status:** IMPLEMENTED — externalize every user-facing string in `crates/tui` to an `en` + `es` catalog with locale resolution (`--lang` → saved config → `LANG`/`LC_ALL` → `en`), persistence, fallback, and deliberate server-error handling.

> **Implements:** https://github.com/savvagent/light/issues/2

## Premise corrections

- The issue lists "CLI help in `main.rs`/`config.rs`" among the hardcoded-string locations. The
  ratatui screens (the actual UI path) live in `crates/tui/src/app.rs`; `main.rs` only prints one
  literal (`"Logged out."`) and the clap `--help` text derives from doc comments. clap help is
  compile-time English; it is **out of scope** here (documented non-goal). `config.rs` has one
  programmer-facing URL-validation error, also left English (documented non-goal).
- The server already ships a stable `code` on every error envelope
  (`crates/protocol/src/auth.rs:101`); the TUI's `ApiError` (`crates/tui/src/api.rs:9`) already
  carries `.code` and `.message`, and `ws.rs` synthesizes the client-local codes `bad_message` /
  `ws_closed`. No server change is required.

## Scope

**In:**
- A translation catalog for `en` and `es` covering every user-facing string in `app.rs`
  (screens, field labels, status lines, hints, footer bar, error messages) plus `main.rs`'s
  `"Logged out."`.
- Locale resolution: `--lang` CLI flag → saved config preference → `LANG`/`LC_ALL` environment
  → `en`.
- Persistence of the chosen locale in `~/.config/light-factory/config.json`.
- A runtime `/lang en|es` command (persists too) for in-session switching.
- English fallback for missing translations (never panic, never render the key).
- Translation of server error messages via stable error `code`, with verbatim fallback.

**Out:**
- Server-side localization (error messages stay English on the wire).
- Localizing clap `--help` output (compile-time English; documented non-goal).
- Localizing `config.rs`'s URL-scheme validation error (programmer-facing CLI argument error;
  documented non-goal).
- RTL / plurals / ICU message formatting (simple `{param}` interpolation only).
- Adding a new dependency or crate (the catalog is a hand-rolled static table).

## §1 Catalog and lookup

A new module `crates/tui/src/i18n.rs` holds two static tables `EN` / `ES`, each a
`&'static [(&'static str, &'static str)]` of `(key, text)` pairs using dot-notation keys
(`status.connecting`, `screen.sign_in`, `error.invalid_credentials`). Interpolation uses
`{param}` placeholders.

- `Locale` — `Copy` enum `{ En, Es }` with `Locale::parse(&str) -> Option<Locale>` (lowercase the
  primary subtag before `-`/`_`/`.`; `es-MX` → `Es`, `C.UTF-8` → `None`), and `as_str()`.
- `t(locale, key) -> &'static str` — look up in the locale table, else `EN`, else return the key
  verbatim (a loud developer sentinel, unreachable in production because `EN` completeness is
  test-enforced). Never panics.
- `t_with(locale, key, params: &[(&str, &str)]) -> String` — `t()` + `{param}` substitution.
- `error_message(locale, code) -> Option<&'static str>` — `Some(translated)` when `EN` defines
  `error.<code>`, else `None` (caller surfaces the server message verbatim).

## §2 Locale resolution and persistence

`i18n::resolve_locale(cli, saved, lang_env, lc_all_env) -> Locale` is a pure, fully-testable
function with precedence: `cli` (`--lang`) → `saved` (config file) → `lc_all_env` (`LC_ALL`) →
`lang_env` (`LANG`) → `Locale::En`. Any unrecognized value falls through to the next source.

A new module `crates/tui/src/settings.rs` persists `{ "lang": "…" }` as JSON at
`~/.config/light-factory/config.json` (mirroring `session.rs`'s `$XDG_CONFIG_HOME`/`$HOME`
resolution). It exposes `load_lang() -> Option<String>` and `save_lang(&str) -> anyhow::Result<()>`
with `_at(path)` variants for unit tests.

`main.rs` gathers the real values (CLI flag, settings file, `LC_ALL`, `LANG`) and, when `--lang`
was passed explicitly, persists it. The `/lang` command in `app.rs` mutates `config.lang` and
persists likewise.

## §3 Server error handling

Known stable codes are translated via `error.<code>`: `invalid_credentials`, `email_taken`,
`invalid_email`, `invalid_totp_code`, `invalid_challenge`, `invalid_session`, `invalid_grant`,
`expired_token`, `storage_error`, `internal_error`, `invalid_json`, `network`, `decode`,
`bad_message`, `ws_closed`. Any other code is **surfaced verbatim** from the server's `message`
(English but safe and legitimate).

**Choice (documented):** translate known stable codes; surface anything unrecognized verbatim —
forward-compatible with future server codes, and never invents text for an unknown code. The
client-local `network`/`decode`/`bad_message`/`ws_closed` codes are translated because they are
generated by this client, not the server.

## §4 `Config` and `App` wiring

- `Config` gains a `lang: Locale` field (`crates/tui/src/config.rs`). `from_url` defaults it to
  `Locale::En` (existing tests unaffected); a `with_lang(Locale)` builder sets it.
- `App` (`app.rs`) exposes `self.config.lang` via `t`/`t_with` helpers, and a
  `fn error_text(&self, code, message) -> String` that prefers `error_message(...)` and falls back
  to `message`.
- Every literal in `app.rs` (status lines, screen titles, field labels, hints, footer bar, log
  lines, error/validation messages) is replaced with `self.t(...)` / `self.t_with(...)`.
- `handle_key`'s device-cancel and `handle_server`'s `ws_closed` paths use localized status text
  instead of English literals.
- The field-label alignment hack (`"Code "` with a trailing space) is dropped; labels are now
  `field.code`/`field.name` and localization makes fixed-width alignment moot.

## §5 CLI

`main.rs` gains `--lang <LANG>` (`#[arg(long)] lang: Option<String>`), localized `"Logged out."`
(`logout_done`), and the resolution described in §2.

## Assumptions

- No new dependencies; the catalog is a static table. Rationale: the crate already depends on
  `serde`/`serde_json` (used by `settings.rs`), and a dedicated i18n crate is unnecessary for
  ~60 strings.
- Interpolation is `{param}` string replacement, no ICU/plurals. Rationale: the TUI has no
  pluralization needs.
- `es` is the shipped second locale because the AC names it as the example.
- `--lang` values and config/environment values use the same `Locale::parse` normalization.
- The `/lang` command is included as the in-session control (mirrors the web selector) and is the
  mechanism that makes "persists across sessions" reachable through actual use.
- Best-effort `es` translations; native review later.

## Goal & Success Criteria

Goal: every user-facing TUI string renders in the user's preferred language.

- `en`/`es` catalogs cover every `app.rs` + `main.rs` literal; no English literal remains in the UI path.
- Locale resolves from `--lang` → saved config → `LANG`/`LC_ALL` → `en` (unit-tested).
- The chosen locale persists in `config.json` (round-trip unit-tested).
- Missing `es` keys fall back to English; `t()` never panics (unit-tested).
- Known server error codes render localized text; unknown codes render the server message verbatim.

## Error Handling & Edge Cases

- Unrecognized `--lang`/config/env value → falls through to the next source, never panics.
- Missing config file / unreadable JSON → `load_lang` returns `None`.
- `save_lang` failure (unwritable `~/.config`) → best-effort `let _ =` (locale still applies for
  the session).
- Unknown server error `code` → verbatim message.
- `{param}` with no matching entry → left literal (developer bug, no panic).

## Risks & Open Questions

- The `es` strings are best-effort; a native speaker should review.
- clap `--help` stays English; if product requires localized help later it is a separate change.
